# RouteSense 真实证据版离线评估设计

## 目标

把离线评估页从“合成演示指标页”改为可追溯的真实评估中心。页面只展示已实际运行、可复核的结果；未运行的实验明确标为“待运行”，不以模拟数字代替真实结论。

本轮也修复运行记录读取失败，并让路由规则能关联到评估证据，而不是停留在静态文案。评测集的能力定义、样本数量与评分口径以《评测集 v2 蓝图》为准。

## 不在本轮做的事

- 不改用户侧旅行规划流程、模型密钥或地图功能。
- 不把真实用户聊天记录混入评测数据；评测仅使用 20 条合成、无隐私的标准任务。
- 不让系统根据一次评测自动修改规则；规则变更仍需人工确认与回归验证。

## 真实数据口径

### 当前已具备的证据（v1，保留作历史基线）

- 标准任务集：20 条，覆盖 19 类旅行规划能力。由于多数类别只有一条任务，不能用来比较某一能力类别的稳定表现。
- 开发集：5 条，用于调整路由规则；当前 `route-v1.4` 严格路由通过 5/5。
- 独立集：15 条，不用于继续调同一版本；当前仅完成一次“静态路由基线检查”，结果为 10/15 严格通过、142/147 字段通过。
- 上述基线检查不调用真实模型，因此不能解释为模型回答质量、成本或延迟。

### 正式模型对照（v2）

正式评估固定比较四个策略组：

| 组别 | 策略 |
| --- | --- |
| 全 Mini | 所有任务固定使用轻量模型，不升级。 |
| 全 Lite | 所有任务固定使用通用模型，不升级。 |
| 全 Pro | 所有任务固定使用强推理模型，不升级。 |
| 动态路由 | 按 RouteSense 规则选择模型；质量检查失败时保留上下文与失败原因，最多逐级升级两次（Mini → Lite → Pro）。 |

v2 采用 7 类能力、21 条开发集和 42 条独立正式集。正式运行每组每任务重复 3 次，共 `42 × 4 × 3 = 504` 次模型调用。每一条试次必须保存输入、上下文摘要、路由决定、模型回答、工具轨迹、Token、耗时、成本、评分和问题标签。

## 数据结构与数据流

新增独立的 `evaluation_runs` 表，不复用日常 `model_runs` 表。这样用户真实会话记录与标准评测记录不会混杂。

每条评测运行记录包含：

- `case_id`、`variant`、`trial` 和规则/提示词版本；
- 任务问题与合成上下文；
- 初始路由、最终路由、升级原因与工具轨迹；
- 模型名称、回答、Token、耗时、估算成本；
- 自动检查结果、人工评分、加权质量分、是否成功；
- 问题标签、纠正状态以及关联的后续运行记录。

评测批量运行器读取独立集，按四组策略调用服务端模型接口，并逐条写入 `evaluation_runs`。汇总接口只按已完成记录计算成功率、约束满足率、单次成功成本和 P95 延迟。

如果记录不足一个完整实验批次，页面显示已完成次数和“样本不足，暂不下结论”，而不是展示百分比结论。

## 页面设计

### 离线评估中心

1. 标题改为“同一批任务，比较四种策略。”
2. 顶部“实验状态与证据说明”取代“资产复用 / AgentScope”：显示任务集版本、7 类能力、21/42 划分、四个策略组、计划 504 次、真实已完成次数与最近运行时间。
3. 核心对照展示全 Mini、全 Lite、全 Pro、动态路由四行。未运行时的各指标显示“待运行”；完成后从真实记录计算。
4. 当前“100 条、3 组、300 条结果”和固定 68%/92%/95% 等模拟指标全部移除。
5. “分层诊断”的“主要问题”改为可点击链接。点击后显示真实问题试次清单：任务编号、问题类型、失败字段、模型档位、评分、运行时间，并可继续打开详情。
6. “失败不是脏数据”改为“问题案例与纠正记录”。点击案例后显示：任务输入、初始回答、路由/升级原因、修正后的回答、评分依据和纠正状态。无真实案例时明确显示“尚无已运行案例”。

### 路由策略页

1. 主标题改为“评测驱动，让策略持续校准。”
2. 删除“供应商可替换”及其面向访客的解释性文案。
3. “首版规则字典”改为“评测反馈驱动的路由策略”。
4. 每条规则新增“证据状态”：`初始假设`、`开发集验证` 或 `独立集验证`。有真实证据时显示对应任务编号、问题类型、规则版本与验证日期；没有证据时不把它包装成评测结论。
5. 规则变更流程固定为：问题样本聚合 → 人工提出规则修改 → 开发集回归 → 规则冻结 → 独立集验证 → 生成新版证据卡。

## 运行记录故障修复

运行记录接口读取 `feedback_updated_at`，而线上 `model_runs` 旧表缺少该列，导致查询整体失败。

修复使用一条仅新增列的 D1 前向迁移，并在部署后验证读取与反馈更新。迁移不会删除或覆盖历史记录。因为这是线上数据库结构变更，执行前需要获得 Cloudflare 管理权限或由项目所有者在 D1 控制台确认执行。

## 失败处理与隐私

- 单条模型调用失败时保存错误状态、HTTP 状态和错误信息，其他试次继续执行。
- 评测运行中途停止时可从缺失的 `case_id + variant + trial` 继续，不重复覆盖已完成记录。
- 评测详情只存标准化合成任务；日常用户运行记录保持独立，并继续在开发者视图内查看。
- Token、成本、延迟仅作为评估指标，不保存或展示 API Key。

## 验收标准

1. 页面不再出现“100 条合成任务”“3 个策略组”“300 条原始结果”及固定模拟指标。
2. 核心对照有四个策略组，且只计算真实 `evaluation_runs` 数据。
3. 未运行时显示待运行和完成进度；不能显示编造的质量/成本结论。
4. 可以从问题摘要进入至少一条真实评测详情，并查看任务、回答、路由、评分和纠正状态。
5. 路由规则卡能区分初始假设与已验证证据。
6. D1 迁移后，运行记录列表与反馈更新均可正常读取、保存。
7. 数据集校验、路由基线、页面测试和生产构建全部通过。

## 作品集表述边界

在真实 504 次正式运行完成前，项目可表述为：

> 重构旅游规划能力评测集，定义 7 类核心能力、21 条开发集与 42 条独立正式集；设计四组模型策略的可追溯对照实验，并搭建路由规则、质量、成本、延迟与问题案例的评估框架。

完成正式实验后，才补充四组真实成功率、成本节省和延迟结果。
