# 评测调用兼容性修复说明（2026-09-03）

## 初步发现与复测结果

V2 开发集校准的前 6 条任务中，轻量档和通用档可以完成调用；一旦动态路由进入强推理档，C4 与 C7 均出现零费用、零延迟的失败，C6 在通用档完成一次调用后升级至强推理档也失败。

初步排查发现，评测调用会给强推理档显式发送 `thinking: { type: "enabled" }`，但网站正式对话的已验证调用方式是在强推理档省略该字段。因此先统一了调用方式。C4 的试次 2 复测仍失败，说明该差异不是唯一根因，不能把它写成最终结论。

## 修改目的与后续诊断

调用方式统一的目的是排除一项已知不一致因素。为定位剩余问题，失败时将新增脱敏诊断日志，只记录任务编号、策略、最终档位、错误类别与 HTTP 状态；不记录用户原文、完整请求、密钥或供应商原始错误文本。

下一次复测将依据日志判断是模型 ID 不可用、服务端参数拒绝还是网络/超时，再提出有证据支持的最小修复。

## 修改范围

- 轻量档、通用档：继续显式关闭深度思考，保证成本与速度稳定。
- 强推理档：不再强制传入深度思考开关，由模型服务采用默认兼容行为。
- 失败诊断：只写入 Cloudflare Worker 日志的脱敏结构化字段，不改变用户端回答，也不改变现有评测记录。
- 不修改模型 ID、密钥、路由门槛、数据集或既有评测记录。

## 验证方式

新增自动化测试：强推理档评测不得强制传入深度思考开关；模型失败时必须写入脱敏诊断字段。两项测试均先在旧代码上失败，再在修复后通过。

下一步应在发布后仅重跑此前失败的开发集任务，确认它们能产生可审查记录；正式集四策略对照需要单独确认预算后才可开始。
