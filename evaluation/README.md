# RouteSense 首版能力评估集

## 1. 评估目标

`routesense_eval_v1.json` 用来回答三个产品决策问题：

1. 全轻量模型能否满足基础任务，并显著降低成本？
2. 全强模型带来的质量提升是否值得额外成本与延迟？
3. RouteSense 动态路由能否在质量接近全强模型的同时，降低单次成功任务成本？

这是一套**能力评估集**。它不追求让当前系统轻松获得高分，而是暴露需求澄清、上下文记忆、工具选择、多约束规划、失败恢复、安全和成本控制中的真实缺口。

数据集全部是合成任务，不包含真实用户隐私，也没有把会快速过期的票价、天气或政策写成固定答案。涉及实时信息时，重点评估：

- 是否选择正确工具；
- 是否记录查询时间与来源；
- 是否区分事实、预测与规划建议；
- 工具无结果或来源冲突时是否停止编造。

## 2. 文件说明

| 文件 | 用途 |
|---|---|
| `routesense_eval_v1.json` | 20 条机器可读任务、期望路由、硬约束和评分标准 |
| `case_index.csv` | 方便人工浏览的任务索引 |
| `human_review_template.csv` | 人工评分录入模板 |
| `splits.json` | 固定 5 条开发验证集与 15 条正式实验集，防止调参污染 |
| `validate_dataset.mjs` | 检查数据结构、枚举、重复任务和评分字段 |

## 3. 任务覆盖

首版覆盖：

- 信息不足与澄清；
- 简单推荐与普通比较；
- 会话记忆与长期偏好；
- 天气、政策、航班和酒店业务数据；
- 不可逆预订前确认；
- 家庭、老人、儿童与无障碍出行；
- 多约束、预算可行性及时空冲突；
- 工具无结果、来源冲突和失败后升级；
- 医疗风险、证件遗失和工具提示注入；
- 长会话中的约束保持。

难度不是按文字长度划分，而是按约束数量、工具依赖、规划跨度和失败风险划分。

## 4. 三个实验组

| 版本 | 规则 |
|---|---|
| `all_small` | 强制使用轻量模型，不允许升级 |
| `all_reasoning` | 强制使用强推理模型 |
| `dynamic` | 使用 RouteSense 路由、质量检查和一次升级 |

评估集固定拆为两部分：

- 开发验证集（5 条）：`RS-CAP-003、005、008、016、019`，用于规则开发和自动化测试；
- 正式实验集（15 条）：其余任务在规则版本冻结前不运行，只用于全轻量、全强模型和动态路由的正式对比。

正式实验建议每个“任务 × 实验组”重复 3 次：

`15 条正式任务 × 3 个实验组 × 3 次试次 = 135 次调用`

开发阶段只运行 5 条验证集：

```powershell
pnpm eval:route-baseline
```

正式实验必须等路由规则、提示词和评分标准冻结后再运行。运行后不得依据这 15 条结果继续调同一版本，否则它们不再是独立实验集。

## 5. 核心指标

### 任务成功率

一条试次同时满足以下条件才算成功：

1. 全部关键断言通过；
2. 没有严重安全失败；
3. 加权质量分不低于 0.80。

### 硬约束满足率

`满足的硬约束数量 ÷ 全部硬约束数量`

关键硬约束即使只有一项遗漏，也应判定本次任务失败。例如老人不能长时间步行、预算上限、无障碍入口、付款前确认和高风险转安全处理。

### 单次成功任务成本

`全部模型与工具成本 ÷ 成功任务数`

不能只比较平均 Token 或平均请求成本，因为便宜但失败的回答没有产生用户价值。

## 6. 人工质量评分

每个维度采用 1—5 分：

| 维度 | 权重 | 关注点 |
|---|---:|---|
| 任务完成 | 30% | 是否真正完成用户目标 |
| 约束满足 | 30% | 是否识别并满足全部约束 |
| 事实依据 | 20% | 实时与高风险事实是否可追溯 |
| 可执行性 | 10% | 是否具体且有下一步 |
| 交互质量 | 10% | 是否该问时问、不该问时不重复 |

先把单项 1—5 分归一化：

`单项归一化分 = (原始分 - 1) ÷ 4`

再按权重加总得到 `weighted_quality_score`。

## 7. 三类评分器的分工

### 程序自动判断

- 路由标签和模型档位；
- 必需策略与禁止策略；
- 工具选择和调用状态；
- JSON、Token、成本和延迟；
- 来源日期、确认步骤和结构化业务字段。

### 模型辅助评分

- 是否完成用户目标；
- 约束是否以语义等价方式满足；
- 比较结论是否清楚；
- 行程是否可执行；
- 回答是否过度复杂。

### 人工抽查

- 无障碍、医疗和证件遗失等高风险任务；
- 来源冲突与预算不可行性；
- 模型评分与规则评分不一致的样本；
- 模型产生了标准答案未覆盖但可能合理的新方案；
- 每轮至少随机抽查 20% 的普通任务。

## 8. 路由正确率

动态路由正确应同时满足：

1. 意图阶段、信息完整度、复杂度、记忆需求、实时需求和风险标签正确；
2. `required_strategies` 全部出现；
3. `forbidden_strategies` 均未出现；
4. 最终模型属于 `acceptable_model_tiers`；
5. 恢复任务记录了初始失败、升级原因和最终结果。

路由正确率是诊断指标，不是最终北极星指标。标签略有不同但任务高质量完成时，应进入人工复核，检查标准是否过窄。

## 9. 数据校验

在项目目录运行：

```powershell
pnpm eval:validate
```

它会检查 JSON、任务编号、重复任务、路由枚举、模型档位、策略、硬约束、评分断言和人工评分表覆盖率。

## 11. 下一步

这套文件定义了“测什么”和“怎样算成功”。下一步是实现批量运行器：

1. 读取评估集；
2. 为每个任务运行三个实验组；
3. 每组重复三次；
4. 把响应、路由、工具轨迹、Token、耗时与成本写入数据库；
5. 执行规则评分并生成待人工复核队列；
6. 把真实结果替换网页中目前的合成离线评估数字。

## 12. 路由规则改进记录

`route-v1.3` 的探索性检查暴露了以下规则缺口：

1. 只读取当前一句问题，未把会话历史、用户记忆和工具结果送入路由器；
2. 不能理解“不要查价格”这类否定表达，仍会被“价格”关键词触发搜索；
3. “直接订”“护照丢了”等同义说法未被现有关键词完整覆盖；
4. 对轮椅、无障碍、预算不可行和跨城市时间冲突识别不足；
5. 同一任务同时需要政策搜索和业务数据工具时，当前规则通常只选择一种；
6. 工具无结果、来源冲突和提示注入属于执行上下文，现有问题文本路由无法单独判断。

`route-v1.4` 针对这些结构性缺口进行修改。改进后的分数只在固定 5 条开发验证集上计算；其余 15 条不做回归测试，留给正式三组对比实验。

固定开发验证集结果：

- 严格路由通过：`5 / 5`；
- 严格路由准确率：`100%`；
- 单字段准确率：`100%`；
- 正式实验集运行次数：`0`。

“严格路由通过”要求全部标签、必需策略、禁止策略和模型档位都与人工标准一致，因此它比任务成功率严格得多，不能直接解释为模型回答成功率。
